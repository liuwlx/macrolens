# MacroLens 多线程组织运行手册

## 1. 组织模型

MacroLens 使用四个互相独立的项目统筹主线程和一个共享的专业部门池。主线程按用户任务临时组建团队；部门席位长期保留领域上下文，但同一时间只能服务一个任务。所有常驻主线程和部门线程在空闲时都使用项目本地环境，不预先创建 worktree。

主线程负责探索、任务拆解、选人、跟踪、验收和最终汇总，不长期直接编码。部门线程负责专业分析、实现或复核。集成发布部是唯一负责把部门提交整合进基线分支的部门。

## 2. 席位状态

- `IDLE`：可以接单。
- `RESERVED`：已经收到完整任务卡。
- `RUNNING`：正在分析或实施。
- `REVIEW`：实现完成，等待测试、审查或集成。
- `BLOCKED`：缺少用户决策、权限或外部条件。

主线程派单前必须通过任务列表和线程详情核实状态。不得把新任务发送给非 `IDLE` 席位。线程运行状态是占用事实来源，不维护另一份手工排班表。

```text

```

缺少任务 ID、成功标准、修改范围或验收检查时，部门应拒绝实施并向来源主线程返回缺失项。

## 4. 标准工作流

1. 用户把一个目标交给任意空闲主线程。
2. 主线程检查当前代码和文档，形成任务卡并选择最小必要部门组合。
3. 产品、宏观研究或架构部门在需求和边界不清时先给出约束。
4. 任务进入实际编码阶段时，才把承担编码的部门席位 handoff 到独立 worktree；分析和待命阶段不创建 worktree。
5. 测试部执行与风险相称的单元、契约、E2E、全栈或数据审计。
6. 权限、数据许可、外部输入或生产部署相关任务由安全合规部复核。
7. 集成发布部审查提交、解决冲突、运行完整门禁并整合到基线。
8. 运维部负责运行、部署和运行后验证。
9. 知识管理部或任务执行部门把结论写入 `docs/conclusions`。
10. 来源主线程向用户交付，并释放所有参与席位。

## 5. 推荐调度组合

| 任务类型 | 最小部门组合 |
|---|---|
| 纯 UI | 产品部 + 研发部 + 测试部 |
| API 功能 | 架构部 + 研发部 + 测试部 |
| Provider 接入 | 数据源部 + 数据平台部 + 研发部 + 测试部 |
| 数据规则 | 数据平台部 + 宏观研究部 + 测试部 + 集成发布部 |
| AI/RAG | AI与文档部 + 研发部 + 安全合规部 + 测试部 |
| 生产上线 | 运维部 + 安全合规部 + 测试部 + 集成发布部 |

## 6. Git 与集成规则

- 常驻线程默认使用项目本地环境；空闲、需求分析、派单和只读检查不得提前创建 worktree。
- 只有正式任务卡明确进入编码阶段后，才把对应席位 handoff 到独立 worktree。
- 不允许两个正在编码的线程共享同一个 worktree。
- 开始前记录基线提交；完成后提供一个或多个清晰提交 SHA。
- 部门线程不得自行合并到基线，不得推送远程或部署，除非任务卡明确授权。
- 集成发布部负责 cherry-pick 或合并、公共契约同步、冲突处理和回归验证。
- 集成完成后，原部门线程从 worktree handoff 回本地项目，确认任务提交已完成整合，再回到 `IDLE`。
- 任何数据库迁移、公共 API、OpenAPI 或 SDK 变更必须由架构部和集成发布部共同验收。

所有实质性工作继续遵守根目录 `AGENTS.md`，尤其是不可变 observation vintage、数据血缘、派生公式版本、预测快照、许可控制、AI 证据、工作区所有权和测试要求。
