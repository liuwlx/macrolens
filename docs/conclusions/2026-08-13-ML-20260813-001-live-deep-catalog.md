## 1. 本次遇到的问题以及场景

Live 数据浏览器把“目录里是否存在一个指标”和“该指标是否已有可读取数据”混为一谈。数据库读取只保留 `active` 且具有唯一 `verified primary` 来源的序列，seed 又只创建一层主题节点，造成 source registry 与 taxonomy registry 中完整的 61 项目录在 Live 模式下被截断。全局树搜索还直接返回所有命中节点，破坏了“每次只返回当前父节点直系子节点”的接口合同。

目标场景要求未映射、缺凭据、待许可和未采集指标仍留在原有深层目录位置，但任何数值读取、导出、比较、历史、AI 上下文和发布能力都不能被误判为已就绪；registry、树、列表、筛选和计数必须共享同一事实集合。

## 2. 分析这个问题的过程

仓库事实核对得到以下结论：

- `source_registry.json` 声明并实际包含 61 个唯一 canonical code；`taxonomy_registry.json` 也声明 61 个，且两者集合完全相同。
- taxonomy 的最深受控路径为 `root → inflation → pce → pce-core → pce-core-services → pce-core-services-nonhousing → pce-medical → pce-medical-hospital`，原 seed 没有使用该结构。
- 61 项 mapping 状态为：READY 31、NEEDS_METADATA_MAPPING 24、NEEDS_DIMENSION_MAPPING 2、LEGAL_REVIEW_REQUIRED 2、LICENSE_REQUIRED 2。
- Live candidate 查询同时依赖 `Series.status == active`、`SourceSeries.is_primary` 和 `mapping_status == verified`，所以目录可见性被采集准备状态截断。
- demo 树接口已有正确的“命中集合向祖先闭包传播、响应仍只返回直系子节点”模式，Live 路由没有复用这一语义。
- 单独保留两条 binding seam 最清晰：`catalog_binding` 只负责目录元数据与筛选；`binding` 仍只接受唯一、已验证主来源，继续控制观测读取、lineage 和许可。

最终采用受控 registry 作为目录 control plane：启动/seed 时验证 61 项、唯一性、无环、唯一 taxonomy owner 和深度；Live API 再对数据库投影进行 61 项、节点结构及 owner 对账，不一致就返回 503，禁止静默发布部分目录。

## 5. 值得沉淀的经验或者模式

- 目录可见性、来源映射、采集凭据、观测存在性和用途级许可是五个不同维度；用一个 `active` 布尔值承载它们会系统性丢目录或误开能力。
- 同一指标应同时拥有“目录 binding”和“数据 binding”：前者允许未就绪元数据可见，后者必须保持唯一 verified primary，天然形成 fail-closed 边界。
- registry 不应只是 seed 输入；API 发布前也要对数据库投影做集合、结构和 owner 对账。否则 seed 漂移会以“部分成功”的形式泄漏到用户端。
- 树搜索的结果应是命中叶子的祖先闭包，但每次接口响应仍必须只含当前父节点的直系子节点；筛选、计数和列表必须从同一个 active set 派生。
- 在脏主工作区上执行任务时，先固定基线、分支和隔离 worktree，再把所有产品命令显式绑定 workdir，可以把用户资产保护变成可验证事实。
- 全量门禁失败必须区分本票回归、既有基线和命令入口错误；对既有失败在基线只读复现，比简单标注“非本票问题”更可靠。
