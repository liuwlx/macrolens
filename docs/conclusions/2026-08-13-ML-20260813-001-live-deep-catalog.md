## 1. 本次遇到的问题以及场景

Live 数据浏览器把“目录里是否存在一个指标”和“该指标是否已有可读取数据”混为一谈。数据库读取只保留 `active` 且具有唯一 `verified primary` 来源的序列，seed 又只创建一层主题节点，造成 source registry 与 taxonomy registry 中完整的 61 项目录在 Live 模式下被截断。全局树搜索还直接返回所有命中节点，破坏了“每次只返回当前父节点直系子节点”的接口合同。

目标场景要求未映射、缺凭据、待许可和未采集指标仍留在原有深层目录位置，但任何数值读取、导出、比较、历史、AI 上下文和发布能力都不能被误判为已就绪；registry、树、列表、筛选和计数必须共享同一事实集合。

## 2. 分析这个问题的过程

仓库事实核对得到以下结论：

- `source_registry.json` 声明并实际包含 61 个唯一 canonical code；`taxonomy_registry.json` 也声明 61 个，且两者集合完全相同。
- taxonomy 的最深受控路径为 `root → inflation → pce → pce-core → pce-core-services → pce-core-services-nonhousing → pce-medical → pce-medical-hospital`，原 seed 没有使用该结构。
- 61 项 mapping 状态为：READY 31、NEEDS_METADATA_MAPPING 24、NEEDS_DIMENSION_MAPPING 2、LEGAL_REVIEW_REQUIRED 2、LICENSE_REQUIRED 2。
- Live candidate 查询同时依赖 `Series.status == active`、`SourceSeries.is_primary` 和 `mapping_status == verified`，所以目录可见性被采集准备状态截断。
- demo 树接口已有正确的“命中集合向祖先闭包传播、响应仍只返回直系子节点”模式，Live 路由没有复用这一语义。
- 单独保留两条 binding seam 最清晰：`catalog_binding` 只负责目录元数据与筛选；`binding` 仍只接受唯一、已验证主来源，继续控制观测读取、lineage 和许可。

最终采用受控 registry 作为目录 control plane：启动/seed 时验证 61 项、唯一性、无环、唯一 taxonomy owner 和深度；Live API 再对数据库投影进行 61 项、节点结构及 owner 对账，不一致就返回 503，禁止静默发布部分目录。

## 5. 值得沉淀的经验或者模式

- 目录可见性、来源映射、采集凭据、观测存在性和用途级许可是五个不同维度；用一个 `active` 布尔值承载它们会系统性丢目录或误开能力。
- 同一指标应同时拥有“目录 binding”和“数据 binding”：前者允许未就绪元数据可见，后者必须保持唯一 verified primary，天然形成 fail-closed 边界。
- registry 不应只是 seed 输入；API 发布前也要对数据库投影做集合、结构和 owner 对账。否则 seed 漂移会以“部分成功”的形式泄漏到用户端。
- 树搜索的结果应是命中叶子的祖先闭包，但每次接口响应仍必须只含当前父节点的直系子节点；筛选、计数和列表必须从同一个 active set 派生。
- 在脏主工作区上执行任务时，先固定基线、分支和隔离 worktree，再把所有产品命令显式绑定 workdir，可以把用户资产保护变成可验证事实。
- 全量门禁失败必须区分本票回归、既有基线和命令入口错误；对既有失败在基线只读复现，比简单标注“非本票问题”更可靠。

- Windows 上通过 npm 转发复杂参数时需要先验证实际子进程入口和参数；入口失败不得冒充产品 RED。

### 6. 反推的一条更好的初始提示词

请修复 Live 数据浏览器的安全状态判断：当用户通过带指标 ID 的链接直接打开页面时，在目录接口明确返回该指标状态之前，不要请求详情、分析、观测、修订、文档或 AI；目录返回待映射、待凭据、待许可、未采集或历史时点不可用后也继续关闭这些能力。后端只有至少一个观测值真正非空且许可等条件满足时才能显示 available。树接口和指标列表必须用同一份完整分类父子关系、61 项清单和唯一归属校验；数据库任一中间分类被错误移动时两边都返回 503。请先写会失败的后端、Web 和 Chromium 深链测试，再最小修复，补齐待凭据与待许可的可见性、解释和零数据请求断言，最后运行定向与全量门禁、更新原报告并提交到现有独立分支，不要推送、合并、部署或修改数据库。

### 7. 当前方案反思与一次解决的更优方案提示词

当前修复已把关键投影校验集中起来，但 catalog loader 与 taxonomy 路由仍各自查询数据库节点，存在重复 I/O；更优长期方案是一次请求内构造不可变 `ValidatedCatalogProjection`，其中同时包含 registry、数据库 node graph、61 series、owner、catalog/data binding、许可与可展示值摘要，再让 browser、facets、counts、taxonomy children 和单指标能力统一从该投影派生。这样既减少重复查询，也从类型上消除未验证集合被下游消费的可能。

更优提示词：请在一次性 PostgreSQL 测试库和精确基线 worktree 中，用 TDD 建立一个请求级不可变 `ValidatedCatalogProjection`。它在构造时一次验证双 registry 的 61 canonical set、完整 taxonomy parent graph、唯一 owner、唯一 verified data binding、用途级许可和至少一个可展示 observation value；构造失败统一返回 503。taxonomy children、series browser、五类 facets、direct/descendant counts、详情、观测、导出和 AI capability 只能消费该投影，不能各自查询并猜测 readiness。前端只接受 `unknown | catalog_only | data_ready`，只有 data_ready 能发数据能力请求。用延迟 browser 响应的深链网络断言、全 None 观测、任意中间节点重挂、待凭据和待许可先做 RED，再逐项 GREEN；连续 seed 两次证明幂等后运行全量后端、Web、build 和 Chromium 门禁，生成七节报告和一个聚焦提交，不 push、不合并、不部署。

Remediation 风险与后续：当前 Windows 环境未提供一次性 PostgreSQL，因此尚未实测真实 seed 后 node graph 漂移和连续两次 seed 幂等；集成发布线程应在隔离数据库补跑该验收。共享投影校验给 Live browser 增加一次有界 taxonomy node 查询，当前目录规模很小；后续若规模扩大，应在请求级复用投影而不是削弱校验。既有 Ruff、mypy、Web lint 和 FastAPI 路由入口债务仍需另票处理。
