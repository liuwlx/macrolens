# MacroLens 多线程部门工作空间实施报告

日期：2026-08-03

## 1. 本次遇到的问题以及场景

用户希望把 MacroLens 工作空间组织成多个长期 Codex 线程，每个线程代表一个部门席位，并保留多个平级主线程和冗余部门席位，以便未来并行开发。目标组织规模为 4 个项目统筹主线程和 26 个部门席位，共 30 条常驻线程。

实施过程中出现了一个重要理解错误：最初把“常驻部门线程”和“具体编码任务的隔离工作树”混为一谈，尝试在初始化空闲线程时创建 worktree。用户指出 worktree 只应在真实编码任务开始时创建。随后立即停止该流程，核验没有生成真实 worktree，并把组织规则改为“常驻线程使用 local；实际编码时按需 handoff 到 worktree”。

## 2. 分析这个问题的过程

1. 使用 Codex 项目列表确认 `macrolens` 已登记为本地项目，但最初不是 Git 仓库。
2. 检查现有线程，确认当前线程可以作为主线程 01，其他 29 条需要新建。
3. 建立 Git 基线，为未来真实编码任务提供按需 worktree 能力。
4. 将部门结构、任务卡、席位状态和交付协议固化到项目配置与运行手册。
5. 校验部门席位求和时发现原计划存在算术错误：逐项配置为 28 而不是 26。通过把研发部调整为 4 席、测试部调整为 2 席，保持总规模为 4+26=30。
6. worktree 初始化受到用户纠正后，检查 `git worktree list`，确认只有主工作目录，错误排队请求没有落成真实线程或工作树。
7. 改用 `environment: local` 创建常驻线程；创建后又发现部分并发线程标题被委托文本覆盖，因此根据保存的标题—ID 映射逐一强制重命名。
8. 最终按项目路径、标题、线程 ID 和运行状态进行交叉核验。

## 3. 解决这个问题的工作流程

最终落地流程如下：

1. 初始化 Git `main` 分支并建立项目基线提交。
2. 新增 `.codex/organization.toml`，记录组织模型、容量、部门使命和专业锚点。
3. 新增 `docs/organization/README.md`，记录任务卡、状态机、调度、交付和集成规则。
4. 更新 `AGENTS.md`，要求所有部门线程加载组织章程，并明确空闲线程使用 local 环境。
5. 将当前线程重命名为 `ML｜项目统筹部｜主线程｜01`。
6. 在相同本地项目中创建其余 3 个主线程和 26 个部门线程。
7. 为每条线程注入与其部门和专业锚点对应的初始化提示词。
8. 强制校正全部线程标题，并置顶 4 个主线程。
9. 验证 30 个标题无缺失、无重复；29 个新建线程全部进入 `idle`。
10. 验证 Git 只有一个工作目录。未来只有正式任务进入编码阶段时，才对承担编码的线程执行 worktree handoff。

## 5. 值得沉淀的经验或者模式

1. 常驻组织线程和执行隔离环境是两个生命周期：线程可长期存在，worktree 应按编码任务临时创建。
2. 多个平级主线程共享资源池时，席位本身的运行状态应是占用事实来源，避免另建容易过期的手工排班表。
3. 批量创建线程后不能只相信创建 API 的返回标题，必须重新列出线程并用预期标题集合做完整性校验。
4. 组织配置中的声明总数必须通过机器计算验证，不能只靠人工相加。
5. 主线程负责拆解和门禁，专业部门负责领域约束，研发负责实现，测试和集成独立复核，可以降低并行修改相互污染的风险。
6. 项目组织规则应同时存在机器可读配置和人类可读手册，避免只把规则留在某条聊天历史中。

## 6. 反推一条更好的初始提示词

> 请为 MacroLens 当前 Codex 项目创建一个多线程部门工作空间：保留当前线程作为 `ML｜项目统筹部｜主线程｜01`，再创建 3 个平级主线程和 26 个常驻部门线程。所有常驻线程必须使用同一个项目的 local 环境，初始化阶段严禁创建 worktree；只有以后收到明确的实际编码任务时，才把对应部门线程 handoff 到临时 worktree。先把组织结构、任务卡、席位状态、派单、交付和集成规则写入 `.codex/organization.toml` 与 `docs/organization/README.md`，再创建线程并注入部门职责。创建后必须重新列出线程，验证恰好 30 条、标题无重复、29 条新线程均为空闲，并用 `git worktree list` 证明没有提前创建工作树。按 AGENTS.md 生成实施报告。

## 7. 当前场景是否有更优方案及一次解决的提示词

更优方案是把常驻线程作为“部门上下文和调度入口”，把 worktree 视为真实编码任务的临时执行环境。主线程派单时先使用 local 部门线程完成需求、边界和风险分析；只有明确需要写代码的席位才 handoff 到 worktree。集成结束后再 handoff 回 local，保留部门历史而不长期占用工作树。

对应提示词：

> 在当前 MacroLens Codex 项目中落地“常驻部门线程 + 按需编码 worktree”组织。创建 4 个互相平级的主线程和 26 个共享部门席位，总计 30 个线程。空闲、调度、需求分析和只读检查全部在 local 项目中完成；禁止初始化时创建 worktree。任务进入实际编码后，主线程才把指定席位 handoff 到独立 worktree；部门提交 commit SHA，由集成发布部合并，完成后线程返回 local。请先机器校验部门席位合计，再创建线程；创建后强制设置标题并按项目路径、标题集合、状态和 `git worktree list` 做最终验收。将全部规则固化到仓库并生成 conclusions 报告。

- 标题检查：无缺失、无重复。
- 环境：全部常驻线程使用项目 local 环境。
- Git worktree：只有 `E:/workerspace/projects/20260709/macrolens` 主目录，没有提前创建额外工作树。
